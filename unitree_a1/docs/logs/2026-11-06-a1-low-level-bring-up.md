## Format บนสาย

Sport controller ส่งคำสั่งจาก `192.168.123.161:8008` ไป `192.168.123.10:8007` และรับ state กลับ ซึ่ง driver ของเราใช้พอร์ต 8080 แทน

**คำสั่ง: 610 bytes, Sport ส่งที่ 500 Hz**

- Byte 0 คือ `0xff` (low-level)
- 4 bytes สุดท้ายคือ CRC32 (poly `0x04C11DB7`) ของ word ก่อนหน้าทั้งหมด ตรวจกับแพ็กเก็ตจริงแล้วตรงกัน
- Record ของ motor เริ่มที่ offset 10, ห่างกัน 27 bytes, มี 20 ช่อง โดยช่อง 12 ขึ้นไปส่ง `PosStopF` / `VelStopF`

| Offset ใน record | Field | การเข้ารหัส |
| --- | --- | --- |
| +0 | mode | `0x0A` |
| +1 | q | float32 |
| +5 | dq | float32 |
| +9 | tau | int16, × 256 |
| +11 | Kp | int16, × 32 |
| +13 | Kd | int16, × 16 ตัดเศษ |

ยืนยันสเกลโดยส่งผ่าน SDK ไป loopback: `tau 1.5 → 384`, `Kp 55 → 1760`, `Kd 0.8 → 12` ดังนั้น policy จะได้ Kd จริง 0.75

**State: 820 bytes, ราว 1 kHz**

`q` อยู่ที่ offset 64, ห่างกัน 32 bytes โดยมี `dq` ที่ q+4 (float32) และ torque ที่ q+10 (int16, ÷ 256)

**SDK แปลงให้เอง:** struct ใน header มีขนาดต่างจากบนสาย (`LowCmd` 730, `LowState` 891, `MotorCmd` 33, `MotorState` 38 bytes) แต่ `UDP(LOWLEVEL)` ส่งได้ 610 bytes พร้อม `0xff` และ CRC ถูกต้อง ทดสอบใน network namespace ที่แยกจาก MCU ส่วน `GetRecv` ถอดรหัสแพ็กเก็ต state จริงได้ตรงกับการอ่าน raw ครบ 12 joint

ผล joint state `FAIL` ใน audit วันที่ 2 พ.ย. จึงมาจากการเดา offset ด้วย struct ใน header ไม่ใช่ encoder หรือ SDK เสีย

## Gain ของ Sport controller

วิธีวัด: ดักแพ็กเก็ตแบบ passive ด้วย `tcpdump` ค่า raw อ่านจากแพ็กเก็ตโดยตรง ส่วนหน่วยจริงใช้สเกลของ SDK โดยถือว่า `A1_sport_1` เข้ารหัสแบบเดียวกัน

| สถานะ | Joint | Kp raw | Kd raw | Kp / Kd | Feedforward |
| --- | --- | --- | --- | --- | --- |
| ลุกและยืน | ทุก joint | 1600 | 48 | 50 / 3 | 0 |
| เดิน: ชุด A | hip | 32 | 16 | 1 / 1 | มี |
| | thigh | 96 | 8 | 3 / 0.5 | มี |
| | calf | 64 | 8 | 2 / 0.5 | เฉลี่ยราว 8.9 N·m |
| เดิน: ชุด B | hip | 32 | 16 | 1 / 1 | มี |
| | thigh | 96 | 32 | 3 / 2 | มี |
| | calf | 64 | 16 | 2 / 1 | มี |
| เดิน: ช่วงสั้น | ทุก joint | 0 | 128 | 0 / 8 | 0 |

- **การตีความ:** ชุด A น่าจะเป็นช่วงรับน้ำหนัก เพราะ feedforward ของ calf สูง และชุด B น่าจะเป็นช่วงยกขา แต่ยังไม่มีข้อมูลสัมผัสพื้นมายืนยัน
- **Gait:** trot โดย FR คู่กับ RL และ FL คู่กับ RR สลับคู่ทุกราว 0.3 s ช่วงสั้นกินเวลาราว 15 ms
- **การตรวจซ้ำ:** ท่ายืน fit Kp จาก `tauEst` ได้ 49.3 (R² 0.998) ตรงกับ 50, Kd ราว 2.95 มาจาก capture ท่าลุกยืนที่ถูกเขียนทับไปแล้ว ส่วนตอนเดิน fit ไม่ตรงกับสเกล จึงยังไม่ถือเป็นการยืนยันอิสระ
- **ท่าลุก:** จากท่านอนไป hip 0, thigh 1.4, calf −2.58 แล้วไป hip 0, thigh 0.8, calf −1.46
- **Peak ตอนเดิน:** `tauEst` ราว 29 N·m และ `dq` ราว 11 rad/s

Sport เดินด้วย gain ต่ำร่วมกับ feedforward torque จึงเป็นคนละวิธีกับ policy ที่เทรนเป็น position PD Kp 50–60, Kd 0.4–0.8 และไม่มี feedforward ค่าตอนเดินจึงใช้แทนค่าของ policy ไม่ได้

## การหยุด Sport mode

`start.sh.desktop` → `start.sh` → `sudo keep_program_alive.sh` → `A1_sport_1` (SCHED_FIFO 99)

ถ้า `A1_sport_1` ตายขณะ supervisor ยังรันอยู่ ระบบจะเปิด `A1_sport_2` ภายใน 0.2 s จึงต้องหยุด supervisor ก่อน ซึ่ง `scripts/sport_mode.sh stop` ทำตามลำดับนี้ และไม่แก้ไฟล์ของ Unitree โดยการรีบูตจะคืน Sport mode

ผลบนหุ่นตอนนอน: หยุดสำเร็จ ไม่มีแพ็กเก็ตไป MCU ตลอด 10 s และ MCU ยังส่ง state ราว 960 Hz

Thigh และ calf ผ่านครบ 8 joint โดยขยับจริงถูกทิศ 0.025–0.099 rad และ joint อื่นขยับไม่เกิน 0.005 rad

### เปิด policy ครั้งแรก (`run_20200606_194857.npz`)

ถูกหยุดด้วย `stale_target` หลังกด `L1 + X` คำนวณ policy ครั้งแรกใช้ 22.55 ms และครั้งถัดไป 0.18 ms ช่องว่างระหว่างคำสั่งจึงเกิน 40 ms ตำแหน่งขาแทบไม่เปลี่ยน ดังนั้น action ของ policy น่าจะยังไม่ถูกใช้กับ motor

แก้โดยคำนวณ policy หนึ่งครั้งตอนโหลด ก่อน motor loop เริ่ม

Action แรกจาก history ที่เป็น 0 มีขนาดถึง 0.605 เช่น `RR_calf` เป้าหมาย −1.158 ขณะที่ `q` อยู่ −1.517 ซึ่งเทียบเป็นราว 20 N·m ที่ Kp 55

รอบถัดไปหลังแก้จุดนี้ โปรแกรมหยุดทันทีหลัง `L1 + X` ด้วยข้อความ `Error: Power Protection.` และไม่มี log จาก disassembly พบว่า SDK `Safety::PowerProtect` พิมพ์ข้อความแล้วเรียก `exit` จึงข้าม damping และ log ทั้งหมด

จึงเอาการเรียกนี้ออก และเพิ่ม fault ใน safety core ที่ตรวจ `sum |tauEst × dq|` เกิน 300 W ต่อเนื่อง 20 ms แทน กำลังอ้างอิงที่วัดได้: Sport mode เดินสูงสุด 139.9 W (เฉลี่ย 20 ms สูงสุด 88 W) และการลุกของเราไม่เกิน 19.1 W ค่า 300 W ยังไม่ได้ตรวจจาก policy จริง

หลังเปิด policy ผู้ทดสอบเห็น `FL_hip` และ `FR_hip` กางออกเร็วมาก ซึ่งตรงกับ action แรก แต่ไม่มี log รอบนั้นเพราะ SDK เรียก `exit` เมื่อจำลองท่ายืนจริงกับ policy พบว่า history ที่เป็น 0 ให้ `ẑ[0]` = 4.96 เทียบกับราว −0.5 เมื่อนิ่ง และสั่ง `FL_hip` ไป +0.243

จึงเปลี่ยนให้ตอนกด `L1 + X` เติม history ด้วยท่าปัจจุบันและ action 0 ซึ่งในการจำลองได้ `FL_hip` −0.024 และ `ẑ[0]` −0.10 **การเริ่มต้นนี้ต่างจากตอนเทรนที่เริ่มจาก 0** และยังไม่ได้ทดสอบบนหุ่น การจำลองยังแสดง `|a|` บางช่องเกือบ 1 แม้ command เป็น 0 โดยยังไม่ทราบว่าเป็น joint ไหนและเกิดบนหุ่นหรือไม่

### Soft-start และ `vx = 0.1` (`run_20200606_194212.npz`)

- **Soft-start 1 s ได้ผล:** ช่วงเริ่ม `tauEst` สูงสุด 7.3 N·m (เดิม 15.7) และ |Δa| สูงสุด 0.049 ต่อ tick (เดิม 0.56)
- **WALK นาน 34.76 s:** ไม่มี fault, inference p99 7.42 ms, กำลังสูงสุด 9.9 W
- **`vx = 0.1` ราว 13 s ไม่เกิดการก้าว:** ผู้ทดสอบเห็นตัวโน้มไปข้างหน้า, action แกว่งไม่เกิน 0.07 rad ที่ราว 0.2 Hz, `|dq|` สูงสุด 1.0 rad/s และ `v̂x` เปลี่ยนจาก −0.09 เป็น −0.03

ยังสรุปไม่ได้ว่านี่คือการเริ่มก้าวหรือการเสียสมดุล

ผลการลดอาการ:

- **กรอง action ที่ α = 0.8:** ที่ command 0.5 และ delay 30 ms ได้ `vx` 0.38, กำลัง 254 W (เดิม 370 W) แต่ที่ 0.4 ไม่เดินเมื่อ delay ≤ 10 ms
- **กรอง action ที่ α = 0.7:** ลดกำลังได้มากกว่า แต่ที่ 0.4 ไม่เดินเมื่อ delay ≤ 14 ms
- **α ≤ 0.5 และจำกัด rate ที่ 0.2 ต่อ tick หรือต่ำกว่า:** แทบไม่เดินที่ 0.5
- **คาดการณ์ `q` ล่วงหน้าเท่า delay:** ไม่ดีขึ้นเมื่อ delay ≤ 10 ms และยังไม่ได้ทดสอบที่สูงกว่านั้น

ลด scale เฉพาะตอนสร้าง target ส่วน policy ยังเห็น action เดิม, `phase2_500` เดิม, ไม่ล้มทุกกรณี (delay 0 และ 10 ms):

| 0.40 | 0.5 | 0.45–0.47 | 4–9% | 23–32 | 143–275 W |
| 0.40 | 0.7 | 0.51–0.59 | 8–13% | 33–34 | 285–338 W |
| 0.35 | 0.7 | 0.56–0.61 | 5–8% | 28–30 | 183–229 W |

Scale ต่ำลงต้องใช้ command สูงขึ้นจึงจะเริ่มก้าว เช่น 0.30 ที่ command 0.5 เดินเมื่อมี delay 10 ms แต่ไม่เดินเมื่อไม่มี delay จึงเพิ่ม `--action-scale` ใน `run.py` ยังไม่ได้ทดสอบบนหุ่น

### เดินได้บนหุ่นที่ action scale 0.2

คำสั่ง: `run.py --stand-time 6 --damping-kd 5 --action-scale 0.2 --tau-limit 40 --power-limit 300 --vx-max 0.7 --vy-max 0.1 --wz-max 0.2`

ผู้ทดสอบรายงานว่าหุ่นเดินได้ เด้งเล็กน้อย ไม่มี fault และออกจาก WALK ด้วยปุ่มตามปกติ แต่เมื่อสั่งเดินตรงมีข้อความว่า "มันหุ่น" ซึ่งน่าจะหมายถึงหุ่นหมุน และยังต้องยืนยัน ไม่มี log รอบนี้ เพราะ `Ctrl-C` ครั้งที่สองขัดการบันทึก จึงแก้ให้ `run.py` ไม่รับ `Ctrl-C` ระหว่างบันทึก log

ผลนี้ต่างจาก MuJoCo ที่ scale 0.2 กับ command 0.7 ไม่ก้าว แสดงว่าหุ่นจริงตอบสนองต่อ action แรงกว่า sim ที่ใช้อยู่ ซึ่งสอดคล้องกับที่หุ่นเด้งหนักกว่าที่ scale 0.4

### เทียบ `ẑ` ของหุ่นจริงกับ sim และช่วงตอนเทรน

### การหมุนซ้ายเกิดใน MuJoCo ด้วย

ทั้งหุ่นและ sim เบนซ้ายเมื่อสั่งเดินตรงโดย wz = 0 วัด 14 s ใน MuJoCo ทุกกรณี (scale 0.25–0.4, command 0.5–0.7, physics 2 และ 5 ms) ได้ +0.05 ถึง +0.13 rad/s เทียบกับหุ่นที่ +0.09 rad/s ในช่วงสั้น 2.4 s และใน sim ทุกขาก้าวเท่ากันราว 5.5 ครั้ง/s

การเบนซ้ายจึงน่าจะเป็นลักษณะของ `phase2_500` ไม่ใช่ sim gap และ**ข้อความใน commit `4657fab` ที่ว่าเบนซ้ายเพราะ FL ไม่ยกเป็นข้อสรุปที่เกินหลักฐาน** ส่วน FL ที่ไม่ยกบนหุ่นยังเป็นคนละเรื่องที่ต้องตรวจต่อ

## Safety ปัจจุบัน

Fault ทุกแบบ latch แล้วเข้า damping (`Kp = 0`, ค่าเริ่มต้น `Kd = 1`) ซึ่งชะลอแต่ไม่ได้พยุงตัวหุ่น:

- ไม่มี target ใหม่เกิน 40 ms หรือ state ค้างเกิน 50 ms
- Roll หรือ pitch เกิน 0.5 rad, `dq` เกิน 30 rad/s, `tauEst` เกิน 30 N·m
- `sum |tauEst × dq|` เกิน 300 W ต่อเนื่อง 20 ms
- Target หรือ gain ไม่ถูกต้อง, `L2 + B`

ข้อจำกัดที่ทราบ:

- ค่าใหม่ของ tilt, torque และ `damping_kd` ผ่านแค่ test บน laptop ส่วน tilt กับ torque ยังไม่เคยทำงานจริงบนหุ่น
- `L2 + B` ต้องผ่าน MCU และโปรแกรมเรา จึงไม่ใช่ E-stop ฮาร์ดแวร์
- Driver อยู่ใน process เดียวกับ Python ถ้า segfault หรือ `kill -9` จะไม่มี damping ชุดสุดท้าย และจากผลข้างต้นขาจะไม่มีแรงถือท่า หุ่นที่ยืนอยู่จึงน่าจะทรุด
- พฤติกรรมของ MCU ที่ Kp สูงและขณะรับน้ำหนักยังไม่ได้ทดสอบ

## งานที่เหลือ

1. ทดสอบการหยุดตอนยืน: `L2 + B` และ tilt fault ขณะ motor มีแรง
2. เปิด policy บนพื้นโดยไม่มีสายรั้ง ซึ่งผู้ใช้ยอมรับความเสี่ยงที่หุ่นล้ม: command 0 แล้วค่อยเดินช้า ๆ และวัดเวลา policy บน Atom
3. เทียบ Kd 0.8 กับ 3 ใน MuJoCo ถ้าขาสั่นหลังเปลี่ยนเป็น gain ของ policy
4. ตั้งนาฬิกาของหุ่นก่อนเก็บข้อมูลเพื่อใช้อ้างอิง
