## Format บนสาย

Sport controller ส่งคำสั่งจาก `192.168.123.161:8008` ไป `192.168.123.10:8007` และรับ state กลับ ซึ่ง driver ของเราใช้พอร์ต 8080 แทน

**คำสั่ง: 610 bytes, Sport ส่งที่ 500 Hz**

- Byte 0 คือ `0xff` (low-level)
- 4 bytes สุดท้ายคือ CRC32 (poly `0x04C11DB7`) ของ word ก่อนหน้าทั้งหมด ตรวจกับแพ็กเก็ตจริงแล้วตรงกัน
- Record ของ motor เริ่มที่ offset 10, ห่างกัน 27 bytes, มี 20 ช่อง โดยช่อง 12 ขึ้นไปส่ง `PosStopF` / `VelStopF`

| Offset ใน record | Field | การเข้ารหัส |
| --- | --- | --- |
| +0 | mode | `0x0A` |
| +1 | q | float32 |
| +5 | dq | float32 |
| +9 | tau | int16, × 256 |
| +11 | Kp | int16, × 32 |
| +13 | Kd | int16, × 16 ตัดเศษ |

ยืนยันสเกลโดยส่งผ่าน SDK ไป loopback: `tau 1.5 → 384`, `Kp 55 → 1760`, `Kd 0.8 → 12` ดังนั้น policy จะได้ Kd จริง 0.75

**State: 820 bytes, ราว 1 kHz**

`q` อยู่ที่ offset 64, ห่างกัน 32 bytes โดยมี `dq` ที่ q+4 (float32) และ torque ที่ q+10 (int16, ÷ 256)

**SDK แปลงให้เอง:** struct ใน header มีขนาดต่างจากบนสาย (`LowCmd` 730, `LowState` 891, `MotorCmd` 33, `MotorState` 38 bytes) แต่ `UDP(LOWLEVEL)` ส่งได้ 610 bytes พร้อม `0xff` และ CRC ถูกต้อง ทดสอบใน network namespace ที่แยกจาก MCU ส่วน `GetRecv` ถอดรหัสแพ็กเก็ต state จริงได้ตรงกับการอ่าน raw ครบ 12 joint

ผล joint state `FAIL` ใน audit วันที่ 2 พ.ย. จึงมาจากการเดา offset ด้วย struct ใน header ไม่ใช่ encoder หรือ SDK เสีย

## Gain ของ Sport controller

วิธีวัด: ดักแพ็กเก็ตแบบ passive ด้วย `tcpdump` ค่า raw อ่านจากแพ็กเก็ตโดยตรง ส่วนหน่วยจริงใช้สเกลของ SDK โดยถือว่า `A1_sport_1` เข้ารหัสแบบเดียวกัน

| สถานะ | Joint | Kp raw | Kd raw | Kp / Kd | Feedforward |
| --- | --- | --- | --- | --- | --- |
| ลุกและยืน | ทุก joint | 1600 | 48 | 50 / 3 | 0 |
| เดิน: ชุด A | hip | 32 | 16 | 1 / 1 | มี |
| | thigh | 96 | 8 | 3 / 0.5 | มี |
| | calf | 64 | 8 | 2 / 0.5 | เฉลี่ยราว 8.9 N·m |
| เดิน: ชุด B | hip | 32 | 16 | 1 / 1 | มี |
| | thigh | 96 | 32 | 3 / 2 | มี |
| | calf | 64 | 16 | 2 / 1 | มี |
| เดิน: ช่วงสั้น | ทุก joint | 0 | 128 | 0 / 8 | 0 |

- **การตีความ:** ชุด A น่าจะเป็นช่วงรับน้ำหนัก เพราะ feedforward ของ calf สูง และชุด B น่าจะเป็นช่วงยกขา แต่ยังไม่มีข้อมูลสัมผัสพื้นมายืนยัน
- **Gait:** trot โดย FR คู่กับ RL และ FL คู่กับ RR สลับคู่ทุกราว 0.3 s ช่วงสั้นกินเวลาราว 15 ms
- **การตรวจซ้ำ:** ท่ายืน fit Kp จาก `tauEst` ได้ 49.3 (R² 0.998) ตรงกับ 50, Kd ราว 2.95 มาจาก capture ท่าลุกยืนที่ถูกเขียนทับไปแล้ว ส่วนตอนเดิน fit ไม่ตรงกับสเกล จึงยังไม่ถือเป็นการยืนยันอิสระ
- **ท่าลุก:** จากท่านอนไป hip 0, thigh 1.4, calf −2.58 แล้วไป hip 0, thigh 0.8, calf −1.46
- **Peak ตอนเดิน:** `tauEst` ราว 29 N·m และ `dq` ราว 11 rad/s

Sport เดินด้วย gain ต่ำร่วมกับ feedforward torque จึงเป็นคนละวิธีกับ policy ที่เทรนเป็น position PD Kp 50–60, Kd 0.4–0.8 และไม่มี feedforward ค่าตอนเดินจึงใช้แทนค่าของ policy ไม่ได้

## การหยุด Sport mode

`start.sh.desktop` → `start.sh` → `sudo keep_program_alive.sh` → `A1_sport_1` (SCHED_FIFO 99)

ถ้า `A1_sport_1` ตายขณะ supervisor ยังรันอยู่ ระบบจะเปิด `A1_sport_2` ภายใน 0.2 s จึงต้องหยุด supervisor ก่อน ซึ่ง `scripts/sport_mode.sh stop` ทำตามลำดับนี้ และไม่แก้ไฟล์ของ Unitree โดยการรีบูตจะคืน Sport mode

ผลบนหุ่นตอนนอน: หยุดสำเร็จ ไม่มีแพ็กเก็ตไป MCU ตลอด 10 s และ MCU ยังส่ง state ราว 960 Hz

ดังนั้นผลนี้ยืนยันว่าคำสั่งไปถูก joint, ถูกทิศ และสเกล gain ถูกในระดับคร่าว ๆ แต่ยังไม่ยืนยันว่าขาเคลื่อนที่ตามคำสั่ง

### บนกล่อง เท้าลอย (`motor_probe.py --box`, Kp 15, 0.1 rad, hip ถือตำแหน่งเดิม)

Thigh และ calf ผ่านครบ 8 joint โดยขยับจริงถูกทิศ 0.025–0.099 rad และ joint อื่นขยับไม่เกิน 0.005 rad

`tauEst` ตรงกับ `Kp × error` ที่เหลือหลายข้อ เช่น FL_thigh 0.89 เทียบกับ 0.86 และ RR_thigh 1.10 เทียบกับ 1.13 จึงยืนยันสเกล Kp ได้ดีขึ้น ส่วนขาไม่ถึงเป้าเต็มน่าจะมาจากแรงเสียดทานหรือน้ำหนักขา โดย `tauEst` ค้างราว 1 N·m ที่ thigh

ยังไม่ได้ทดสอบการขยับของ hip เพราะกล่องกีดขวางทางหุบเข้า ส่วนเครื่องหมายของ hip มีหลักฐานจาก `tauEst` รอบท่านอนเท่านั้น

### เมื่อโปรแกรมตายขณะ `Kp > 0` (`kill -9`, Kp 15, ดันขาด้วยมือ)

| ช่วง | ผล |
| --- | --- |
| ก่อน kill | ดันแล้วมีแรงดึงกลับ |
| หลัง kill | ไม่มีแรงดึงกลับ แต่ขายังฝืด |

จึงน่าจะไม่ได้คงคำสั่ง Kp สุดท้ายไว้ แต่เข้าสู่สถานะคล้าย damping ผลนี้ประเมินด้วยมือ ยังไม่รู้ว่าใช้เวลาเปลี่ยนนานเท่าไร ความหน่วงเท่าไร และยังไม่ได้ทดสอบที่ Kp 55 หรือขณะรับน้ำหนัก

### ลุกและยืนบนพื้น ไม่มี policy

คำสั่ง: `run.py --stand-only --power-level 1 --stand-time 6 --damping-kd 5` (ลุกด้วย Kp 50, Kd 3)

- **ผลจากหน้าจอ:** ไม่มี fault, `SCHED_FIFO` ใช้งานได้, overrun เป็น 0 และ motor loop ช้าสุด 2.02 ms
- **ผลจากการสังเกต:** ลุกและยืนได้ และทรุดลงด้วย `L1 + B` อย่างนุ่มนวล ไม่ได้จับเวลาการยืน
- **ยังไม่ได้วิเคราะห์:** tracking, torque และความนิ่ง เพราะ `run_20200606_214211.npz` ยังอยู่บนหุ่น

## Safety ปัจจุบัน

Fault ทุกแบบ latch แล้วเข้า damping (`Kp = 0`, ค่าเริ่มต้น `Kd = 1`) ซึ่งชะลอแต่ไม่ได้พยุงตัวหุ่น:

- ไม่มี target ใหม่เกิน 40 ms หรือ state ค้างเกิน 50 ms
- Roll หรือ pitch เกิน 0.5 rad, `dq` เกิน 30 rad/s, `tauEst` เกิน 30 N·m
- Target หรือ gain ไม่ถูกต้อง, SDK PowerProtect, `L2 + B`

ข้อจำกัดที่ทราบ:

- ค่าใหม่ของ tilt, torque และ `damping_kd` ผ่านแค่ test บน laptop ส่วน tilt กับ torque ยังไม่เคยทำงานจริงบนหุ่น
- `L2 + B` ต้องผ่าน MCU และโปรแกรมเรา จึงไม่ใช่ E-stop ฮาร์ดแวร์
- Driver อยู่ใน process เดียวกับ Python ถ้า segfault หรือ `kill -9` จะไม่มี damping ชุดสุดท้าย และจากผลข้างต้นขาจะไม่มีแรงถือท่า หุ่นที่ยืนอยู่จึงน่าจะทรุด
- พฤติกรรมของ MCU ที่ Kp สูงและขณะรับน้ำหนักยังไม่ได้ทดสอบ

## งานที่เหลือ

1. ดึง log การยืนมาวิเคราะห์ tracking, torque และความนิ่ง และวัดเวลา policy บน Atom

3. เท้าลอยและรัดลำตัว: เปิด policy ด้วย `--action-clip` และ `--kp` ที่ต่ำ แล้วค่อยเพิ่มถึงค่าจริง
4. มีสายรั้ง: เปิด policy บนพื้นด้วย command 0 แล้วค่อย `vx = 0.1`
